# 文案与节奏

## 容量参考

45–60 秒通常 3–5 组更新、10–14 个镜头。这是容量参考，不是要填满的模板：小版本 20 秒也行。**先估阅读与演示时间，再贴合音乐**，不要先锁死 48 秒再塞字。

"主张 → 证明"结构的段落参考：开场一句直接的变化（2–4 秒）→ 每组核心能力：字卡提出 → 组件特写证明 → 工作区交代上下文（7–12 秒）→ 小优化 2–3 个（各 2–4 秒）→ 收尾：产品标识 + 一句收束（2–3 秒）。

镜头变化来自"要让观众看哪里"，不是用随机转场制造忙碌。

## 双语标题分工

- 默认：**英文短标题**（提炼能力/动作）+ **中文标题**（让人直接懂）+ **中文说明**（对象 + 动作 + 结果）。
- 英文、中文各一个 span，分别指定 `--font-en`、`--font-zh`，不要让 fallback 随机分配字形。中文用无衬线；英文可衬线或按品牌选。
- 英文要贴合功能、有实际语义；不机械翻译中文长句，不硬塞空口号（NEW! / Powerful）。中文说明不看英文也能独立理解。
- 字体来自产品或有授权的字体；正式工程冻结字体文件，截帧确认实际字形，不能只看 CSS 字体名。
- 用户指定单语/字体时照办，记录在 `plan.json.typography.exceptionReason`。

## 上屏文字要自己能讲完故事

静音自动播放是常态：每个功能主张都要有上屏文字，关掉声音也能看懂。开场句 ≤ 约 15 字，1.5 秒内读完。有旁白时，把旁白要点做成 supers（关键词 + 短句），不要整段字幕墙；旁白与上屏文字说的是同一件事，不各说各的。

## 说人话

| 过于省略 | 更清楚 |
|---|---|
| 上下文，跟得上。 | 更换模型后，可以带着之前的对话继续工作。 |
| 让工作流自然流转。 | 提交修改后，在同一个窗口就能看到检查结果。 |
| 结果，触手可及。 | 任务完成后，点通知就能回到对应的对话。 |

以上是写法示例，**只有功能真实存在时才能用**。功能名与真实界面一致，不改成"更聪明、更丝滑"这类无法证明的词。

## 试读（写入 `evidence/copy-review.md`）

逐项：

1. 先写白话事实："以前要做什么，现在怎么做，结果有什么不同。"不知道以前的行为就不编对比。
2. 从中提炼标题，再写说明（对象 + 动作 + 可观察结果）。
3. 遮住画面和英文，只读中文给没用过产品的人听；对方还要问"什么接上了？在哪看？会发生什么？"就重写。
4. 标题和说明不能是同义重复。
5. 用聊天语气念一遍，检查上屏时长。

`plainExplanation` 存白话事实，`description` 是上屏文字；不能为了"高级感"把具体解释压回抽象短语。

## 动作、停留、音乐

- 入场/选中/切换动作 0.25–0.6 秒，有明确起止。
- 每个镜头：建立画面 → 核心动作 → 可读结果 → 切走。不要所有元素一起飘入再静止 5 秒。
- 说明**早出现**，让阅读与演示重叠。长句靠删词、分句、加停留解决，不靠缩字号。
- 读速预警线：每秒约 6–9 个中文字（界面同时复杂变化时再留余量）。这是人工起点，不是通过阈值。
- 编曲可从 110–125 BPM 起；主动作贴重拍，小动作错半拍。不要把所有镜头量化成同样长度。
- 短暂停顿用于强调和阅读是对的；警惕无信息的长停顿，但别为了消除"静止"加无意义晃动。
- 结尾要有完整落版和声音收束；不允许链接时只留产品名/Logo 与一句结束语。
